description: Run CI-equivalent checks, run the reviewers, then open the PR with the filled-in template per CLAUDE.md
---
Follow CLAUDE.md "Pull requests" exactly. Never open a PR by hand, and never use a free-form body.

1. Read `.github/pull_request_template.md` first. The PR body is that template, every section filled in. A hook (`.claude/hooks/require_pr_template.py`) refuses to create or edit a PR otherwise, and CI check "PR template filled" fails it. Do not weaken either.
2. Check `git status` and `git log --oneline -15`; the issue must exist on the board and be named in the PR (`Closes #N`).
3. Branch off current `main`; run backend `ruff check .` and `pytest -q` (MACRO_DATA_PROVIDER=none) and, for frontend changes, `tsc --noEmit`, `npm run lint`, `npm test`, `npm run build`. Tick only what ran.
4. Run the reviewers the change calls for: `rules-auditor` (any backend, prompt or schema change), `docs-sync-checker` (any backend or docs change), and `playtest-qa`, `game-ux-designer`, `game-designer`, `game-feel-engineer` (any game UI change); the `qa-testlead` row is for the repo skills `qa-testlead` / `code-auditor` when the work calls for them, otherwise `skipped` with the reason. Also: `release-manager` (CI, Docker or migration files; and before Faiz merges), `llm-quality-guard` (a prompt or analysis schema), `valuation-reviewer` (valuation, DCF, risk-band or financial-metric code, and any sentence about what a number does), `compliance-officer` (a new dependency, data provider or LLM client, or a change to what is stored or logged), `board-steward` (every PR, last: issue, milestone, labels, stacked PRs). The checker refuses `skipped` for the first four when those paths changed. Fix findings, re-run only what failed (max 2 rounds, then ask Faiz).
5. Check every claim in the docs and the PR body against the code in this session (CLAUDE.md "Pull requests" step 4). Mirror new or changed `docs/` files to the Claude project as `claude/<name>.md` in the same change. `docs/PROGRESS.md` is only a pointer to the board; do not add status to it. Update the issue and milestone instead.
6. Fill every row of the "Who reviewed it (agents and skills)" table with what actually ran and a result or link; write `skipped` and the reason for anything that did not. Never mark a role as run when it was not.
7. Commit, push, open the PR through the GitHub REST API with the body file (`--input`), attach the milestone, watch the checks. Never merge.
